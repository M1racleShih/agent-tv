harness 指支持 agent 持续开发的项目资料、工具、运行环境和检查过程。这里保存 AgentTV 的具体约定。

01 把开发需要的信息与反馈放进项目

你同时使用不同 agent，开发工作可能跨会话、跨工具继续。AgentTV 需要一份易找的项目说明、可维护的执行计划，以及能反映实际状态的检查结果。人负责目标、优先级和影响范围的决定，agent 完成已授权的实现与验证。

参考 OpenAI 的 Harness engineering，这里采用简短入口、项目内知识、可执行约束与可观察结果四个做法。下面的目录、命令和验收场景根据 AgentTV 的需求制定。Codex 最佳实践也建议把工作方式与验证入口写入项目说明。

首版保持工具精简：开发脚本使用 Python 标准库，产品后端继续使用 Rust，网页使用 Svelte + TypeScript。现有 herdr 与各 agent 的启动方式继续沿用。

02 用短入口找到当前任务需要的资料

位置负责的信息
README.md仓库当前状态、阅读入口、可执行命令和下一步。仓库启动建设的决定与验收见 独立记录。
AGENTS.md共享开发入口：工作步骤、核心行为、检查命令、范围与授权要求。详细说明通过链接查找。

implementation.htmlworkspace 归属、会话与轮次、状态、待处理事项、Record、采集方式和已观察的本机能力。
首轮开发计划这轮产品开发的目标、阶段、完成标准、进度与决定。复杂的新任务按 计划模板另建 HTML 计划。
policy.json机器可读的文档清单、技能与运行产物的忽略规则，以及 Rust 包的依赖方向。

当前任务只读取相关章节和源码。改变需求或行为时，更新对应说明和受影响的场景；例行文案、样式或小范围修复可使用简短的会话计划。

四类 agent 共用这些文件。dskills 继续管理技能的实际安装位置，项目规则和技能内容各自维护。GUI demo 的原文件保持只读；项目内已有布局说明和校验摘要，新的会话可以从这些资料开始。

03 一轮开发围绕可看到的结果推进

  1. 说明结果。写清楚完成后用户能做什么，指向相应验收场景，并说明本次修改哪些模块。
  2. 维护计划。涉及多模块、状态行为、数据库或接入方式时，创建或更新 HTML 计划。记录依赖、风险与验证方式，进度变化时同步更新。
  3. 实现可运行的一步。把数据、服务和必要页面连接起来，尽早使用真实结构的合成样例。常规且可撤销的技术细节由执行 agent 处理。
  4. 检查并修复。运行覆盖本次行为的检查，处理本次改动造成的失败，确认服务或页面实际表现。新行为与回归问题需要能证明结果的测试。
  5. 保存并交付。更新计划与说明，报告做成了什么、实际运行了哪些检查，以及仍未验证的部分。

小范围文档与样式修改按影响选择检查。已有检查继续覆盖最终改动时可以复用结果；相关代码、输入或环境变化后重新验证。发现同类问题反复出现时，将具体原因补进说明或检查程序。

例行开发继续使用已有授权。改变需求覆盖、影响项目外状态或涉及工具审批时，再提出具体决定。子 agent 的使用须获得用户对名称、任务和范围的明确批准。

04 用同一个入口运行本地与 CI 检查

在项目根目录运行，要求 Python 3.11 或更高版本。脚本使用标准库，首次运行即可检查当前项目。

python3 scripts/harness.py doctor
python3 scripts/harness.py check --scope docs
python3 scripts/harness.py check
python3 scripts/harness.py cases
python3 scripts/harness.py check --scope product
命令运行内容与结果含义
doctor读取本机 Python、Git、Rust、Node、npm 与 dskills 状态。确认四类 agent、plain-docs 和 no-track 配置。Git 尚未初始化时说明现状，本地检查仍可使用。
check --scope docs检查 HTML 标签嵌套、链接与锚点、计划必需章节、共享指令入口、忽略规则和场景目录。排版观感与文案由实际阅读和可用的页面工具核查。
check --scope harness包含文档检查，并运行 harness 的自测。自测使用临时文件、合成 Cargo 元数据和短命测试进程。
check包含以上检查。Cargo.toml 存在时运行依赖方向、格式、Clippy 和测试；web/package.json 存在时运行类型检查、测试与构建。尚未创建的产品项目明确显示 NOT_APPLICABLE。
cases列出每个关键场景的测试登记情况。planned 表示仍需编写；registered 表示已有命令，实际结果需要通过运行取得。
check --scope product要求完整 Rust 与网页工程、依赖锁文件、工具链文件和全部关键场景的自动命令，逐项运行并保存结果。缺少任何必要部分时返回失败。

每次运行输出 PASSED、FAILED 或 NOT_APPLICABLE，失败返回非零退出码，并打印 JSON 报告位置。产品尚未创建时，普通检查可以通过；严格产品检查应失败。开发交付说明需要同时说明检查范围和未覆盖能力。

Rust 验证使用 cargo fmt、cargo clippy --locked --workspace --all-targets -- -D warnings 和 cargo test --locked --workspace --all-targets。网页提供非交互的 check、test、build npm scripts，其中测试接受 --run。

创建产品工程时同时保存 Cargo.lock、rust-toolchain.toml、web/package-lock.json 和 web/.node-version。本机与 CI 使用同一检查入口；CI 安装相应工具链和锁定的依赖后运行。当前目录已初始化本地 Git；托管平台与远程 CI 尚未配置。

05 在依赖方向上执行程序边界

产品采用四个 Rust 包与一个网页目录，按首轮计划逐步创建。采集器提供领域观察，数据库保存记录，服务协调两者，网页通过本机接口查看与编辑。

目录与包职责和允许的本地依赖
crates/domain
agenttv-domain		会话、轮次、状态、待处理与 Record 的类型和行为。独立于其他项目包，业务计算保持便于用样例验证。
crates/storage
agenttv-storage		SQLite 保存、修订冲突、查询与恢复。可依赖 domain。
crates/adapters
agenttv-adapters		读取 herdr 和原生数据，检查格式并产生 domain 观察。可依赖 domain。
crates/server
agenttv-server		运行采集、保存观察并提供 HTTP / SSE。可依赖 domain、storage 和 adapters。
webSvelte + TypeScript 页面。通过服务接口取得数据，实现 Preview、Record、搜索与交互。

检查程序读取 Cargo 元数据，验证包的位置和全部本地依赖方向，domain 也检查 Axum、Tokio、rusqlite 等依赖。错误信息指出具体依赖和调整方向。需要改变结构时同时修改设计、policy 和相关检查。

依赖检查覆盖静态包关系。状态是否正确、保存是否可靠和采集能否恢复，由对应场景测试验证。来源数据进入系统时解析并检查格式，未知字段或未知状态保留诊断信息。

06 分别验证样例、真实来源和页面

自动检查使用可丢弃的样例

目前登记了 14 个关键场景，覆盖 workspace、Preview、待处理、Record、搜索与渲染。每个场景有稳定 ID、预期结果与设计章节；实现对应行为时补上实际的自动测试命令。测试应在行为错误时失败，并保证目标测试确实执行。

测试使用合成的会话 ID、文本、JSONL 和 socket 事件，样例明确注明来源格式与模拟内容。进程测试只管理本次创建的进程。临时数据放入独立目录，测试完成后清理自己创建的资源。

harness 启动检查命令时提供 AGENTTV_DATA_DIR、AGENTTV_SOURCE_MODE=fixture 和 AGENTTV_FIXTURES_DIR。产品与测试实现时必须实际遵守这些设置；它们表达运行约定，本身不提供操作系统级隔离。

真实接入单独记录观察

真实来源用于确认安装版本、事件语义、延迟和进程关联，结果记录具体版本、步骤和未覆盖行为。读取历史、添加 hook、创建测试会话与终止测试进程分别说明范围。既有工作会话继续正常运行。

herdr CLI、运行服务和 desktop 内置版本分别记录。缺少字段或连接失败时显示实际能力；状态推断依据保留来源与观察时间。合成样例通过后，真实接入仍需要本机观察支持。

页面交付包含实际使用

页面按你的 demo 布局与视觉方向实现，使用合成内容启动独立开发实例。检查 Preview / Record 切换、快速记录、保存状态、待处理确认、窄屏布局和长文本。浏览器检查使用当次允许的工具，保存必要截图或操作记录。

浏览器工具限制某种 URL 或操作时，记录未验证部分，继续完成源码、类型和可执行测试。工具允许的运行方式准备好后补做页面检查。当前 HTML 文档完成结构和链接检查，实际页面排版仍受 file:// 访问限制。

严格产品检查说明自动验证的结果。五个来源的真实状态准确性和 GUI 的实际观感另列观察记录，交付时一并说明。

07 保存实际结果，方便下个会话继续

每次检查在 .harness/runs/<UTC 时间与唯一标识>/ 保存报告、子命令日志和本次数据目录；各个子命令使用自己的数据子目录。报告记录检查范围、实际命令、运行时长、退出结果，以及关键场景登记数量。目录已加入 Git 忽略，运行记录保留在本机。

执行计划记录可复查的短结果、日期和有关决定。重要失败需要写明如何复现与恢复；产品行为尚未完成时，保持对应步骤未完成。复制终端结果时保留必要信息，真实会话正文与凭据继续留在原有本机数据中。

继续一个任务时，先看计划进度、相关源码和最近结果，再判断旧检查是否仍覆盖当前输入。归档计划时记录实现结果、遗留问题和后续工作；新任务可通过链接找到需要的历史决定。

计划模板包含目的、进度、决定、验证、恢复与结果六部分。格式使用 HTML；较小任务可直接在会话说明目标与检查，避免产生仅为填表的计划。

08 按实际摩擦改进工具与说明

每轮修改结束时检查相邻说明、链接和场景是否受影响。多次出现同一类错误时，优先补上可复现的样例、明确的输入检查或具体的开发说明。规则保持贴近当前工程，失效内容随相关修改更新。

dskills 保持 no-track，当前只安装 plain-docs：Codex、Kimi、pi 共用 .agents/skills，Claude 使用 .claude/skills。新增技能需有具体任务用途；常用命令与短规则优先保留在本项目说明和脚本中。

周期维护目前由实际开发任务触发。后续需要调度自动运行、使用子 agent、发送消息或发布结果时，按用户授权范围和当次工具要求执行。
